# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository

## What this repo is

A single NixOS flake that builds two hosts: `nixos-pc` (NVIDIA/CUDA workstation) and `nixos-laptop` (CPU-only). It is configuration — there is no application code, no test suite, no linter. "Building" the repo means evaluating the flake into a system closure; "running" it means switching to that closure on a NixOS host

## Build / switch / iterate

```sh
# Switch (requires root, only on the matching host)
sudo nixos-rebuild switch --flake .#nixos-pc
sudo nixos-rebuild switch --flake .#nixos-laptop

# Build without activating — works from any machine, useful for CI-style validation
nix build .#nixosConfigurations.nixos-pc.config.system.build.toplevel
nix build .#nixosConfigurations.nixos-laptop.config.system.build.toplevel

# Evaluate without building (fastest sanity check)
nix eval .#nixosConfigurations.nixos-pc.config.system.build.toplevel.drvPath

# Inputs
nix flake update            # all
nix flake update <input>    # one
```

There is no `nix flake check` target wired up and no per-module test — validation is `nix build` of the host closure

## Architecture you must internalize

1. **One flake, two systems.** `flake.nix` defines `nixosConfigurations.nixos-pc` and `nixosConfigurations.nixos-laptop`. There is no separate Home Manager deployment — HM is loaded as a NixOS module via `home-manager.nixosModules.home-manager` with `useGlobalPkgs = true`, so the NixOS and HM layers share one package set and overlays

2. **Two package sources, always be explicit which one you use:**
   - `pkgs` — `nixos-unstable`
   - `pkgs.stable` — the last release of `nixpkgs`, exposed by `overlay-stable` (both hosts)
     Mismatches cause silent rebuilds of huge ML stacks. CUDA workloads come from dedicated nixpkgs attrs (`ollama-cuda`, `btop-cuda`, the `comfyui-nix` flake), not a global `cudaSupport` overlay. CUDA codegen is pinned to the workstation GPU via `cudaCapabilities = [ "8.6" ]` in `nixpkgsConfig` (the shared nixpkgs config; change on GPU swap) — this narrows the arch list without enabling global `cudaSupport`, so only `ollama-cuda` honors it (it misses every cache and always compiles; comfyui pins its own arches and keeps its cachix, btop-cuda ignores the flag). The Jupyter module uses `pkgs.stable.python3` and gates the torch/transformers stack behind `rokokol.jupyter.withTorch` — enabled on the laptop (CPU torch, cached), off on the PC to avoid the from-source CUDA build (`libnvshmem`)

3. **`commonArgs` is the only way arguments cross the flake boundary.** `flake.nix` builds `commonArgs = { rokokolName, huixDir, govnoDir, myWikiDir, system, inputs }` and passes it via both `specialArgs` (NixOS) and `extraSpecialArgs` (HM). Any module can pull these out of its arguments — no need to thread them manually. When you add a new constant that multiple modules need, add it here, not as a `let` binding scattered across files

4. **Host composition is layered. Edit the narrowest layer.**
   - `nixos/configuration-<host>.nix` — the per-host _input_: imports, the one or two settings that genuinely differ (`ollama.package`, `stateVersion`) and the `rokokol.*.enable` flags for host-specific services
   - `nixos/default.nix` — modules shared by both hosts (desktop, fonts)
   - `nixos/<host>/` — host-specific hardware/system/boot/keyboard/options
   - `nixos/services/default.nix` — the single aggregator importing _all_ service modules on both hosts. Shared services are unconditional; host-specific ones are gated by `rokokol.<name>.enable` declared inside their own module. To add/remove a service from a host, flip the flag in `configuration-<host>.nix`
   - `nixos/services/<category>/` — individual service modules, grouped by `ai/`, `desktop/`, `devices/`, `system/`, `tools/`, `utils/`. New services go into the appropriate category and get imported in `services/default.nix`
   - Same shape mirrors on the HM side: `home-manager/home-<host>.nix` is the per-host input (all `rokokol.*` values: hyprland, waybar, packages, dataDir) → shared `desktop/user.nix` → shared `programs/` + `desktop/`

5. **Custom options are namespaced under `rokokol.*` and declared in the module they gate.** NixOS side: `rokokol.jupyter.{enable,withTorch}` plus enable flags for host-specific services (`comfyui`, `openwebui`, `searxng`, `printer`, `tablet`, `virtualization`), set in `configuration-<host>.nix`. HM side: `rokokol.hyprland.*`, `rokokol.waybar.*` (one bar, per-feature component files), `rokokol.packages.{pc,laptop}`, `rokokol.home.dataDir`, set in `home-<host>.nix`. Follow this pattern — don't reach for `mkIf config.services.foo.enable` from another module to gate behavior; expose an option

6. **`useGlobalPkgs = true` consequence.** You cannot set `nixpkgs.config` or `nixpkgs.overlays` inside an HM module — they're ignored. All package/overlay config lives in `flake.nix` (system-level)

## Placement rules

When in doubt where a change belongs:

- **NixOS (`nixos/`)** — boot, hardware, networking, kernel, GPU, system-wide services, users, global security, anything touching `/etc` or systemd-system units
- **Home Manager (`home-manager/`)** — interactive user environment, app config, shell behavior, desktop theming, Hyprland/Waybar, per-user packages, systemd-user units
- **New system service** — new file in the matching `nixos/services/<category>/`, imported in `nixos/services/default.nix`; if it shouldn't run on both hosts, gate it behind `rokokol.<name>.enable` and flip the flag in `configuration-<host>.nix`. Do not collapse multiple services into one module
- **New user app with config** — new file in `home-manager/programs/`
- Do not cross the streams: no HM options under `nixos/`, no system services under `home-manager/`

## Package layering

- System packages and feature toggles → host-specific NixOS modules (`nixos/pc/`, `nixos/laptop/`)
- User-facing shared packages → the common block in `home-manager/desktop/packages/packages.nix`
- Host-specific user packages → the `rokokol.packages.{pc,laptop}` groups in `packages/packages.nix` (flags set in `home-<host>.nix`)
- Always pick the right source: `pkgs` (unstable default), `pkgs.stable` (stability-critical); CUDA workloads use dedicated attrs (`ollama-cuda`, `btop-cuda`, `comfyui-nix`)

## Style

- 2-space indentation, kebab-case file names (`configuration-pc.nix`, `wl-clip-persist.nix`)
- **All repo files are kebab-case**, including assets (`assets/laptop-wallpaper.png`, `assets/say-sketch2.webp`) — no `snake_case`, `CamelCase`, or spaces. When adding a file, name it kebab-case; when renaming, `git mv` and update every reference (grep the whole tree — refs live in `.nix`, `.sh`, `.conf`, README). Deliberate exceptions: conventional metadata docs (`README.md`, `CLAUDE.md`, `AGENTS.md`, `SKILL.md`, `LICENSE`) and vendored upstream fonts under `nixos/fonts/` (canonical branding; referenced by glob, not by name)
- **All text in English.** Prose comments across scripts and Nix modules, plus every user-facing string (notify-send, rofi prompts, `usage()`/help text, waybar tooltips), are written in English; keep new text English and consistent with the surrounding style. The **sole exception is `README.md` files** — those stay in Russian
- **No trailing period at the end of a paragraph.** Periods separate sentences _within_ a paragraph, but the final sentence of a paragraph — and any standalone one-liner (a single-line comment, a list item, a notification, a commit-message line) — gets no closing period. Other terminal punctuation (`?`, `!`, `…`, `:`) is unaffected; an inner sentence still ends with its period before the next one begins. Applies everywhere: comments, issues, UI strings, help text, commit messages (README formatting is owned by the `readme` skill)
- **Quotes are always straight `"…"` — never `«ёлочки»`, `„лапки“` or curly `“…”`**, in every language and every file type: comments, `usage()`/help text, notification and UI strings, commit messages (README formatting is owned by the `readme` skill). When a quote lands _inside_ a string literal, escape it (`"toggle \"lid doesn't sleep\" (laptop only)"` in Nix, `echo "microphone \"$name\""` in bash) — never leave a bare `"` that would terminate the string. Anything mechanical here (a repo-wide replace) must be byte-wise (`\xc2\xab`/`\xc2\xbb`) and check the string-literal cases by hand afterwards
- **Keep comments terse.** A comment states the non-obvious _why_ in as few words as possible — ideally one line. Don't stack multi-line explanations where a short clause does; if a comment needs a paragraph, the code probably needs restructuring instead
- **No dates in comments.** Don't anchor a comment to a moment ("removed on 2026-07-22", "as of the July update") — dates rot and can't be verified from the code later. State the durable reason instead ("removed from nixpkgs because it needed GTK2"). Version pins live in `flake.lock`/`rev`, not in prose
- Small composable modules over monoliths; `default.nix` is reserved for aggregator files that only do `imports = [ ... ]`
- Prefer flake-pure patterns. Avoid `nix-channel`, `NIX_PATH`, `<nixpkgs>`, and other impure references
- Declarative over imperative; reusable over duplicated
- Don't touch `system.stateVersion` / `home.stateVersion` unless doing an explicit migration

## Editing gotchas

- **`backupFileExtension = "bak"`** in `flake.nix` — deliberately a fixed string. A `"bak-${inputs.self.lastModified}"` suffix lands in the activation script, so every commit rebuilt the HM generation (and littered `$HOME` with one `.bak` set per revision). The cost of the fixed string: a second collision on the same path aborts activation (`Existing file '<path>.bak' would be clobbered by backing up …`) until the stale `.bak` is deleted by hand. For a file some app is expected to re-create, don't rely on backups — set `force = true` on the `home.file` entry, which skips the collision check and overwrites (see the MathWorks autostart stub in `packages.nix`)
- **Commit your work yourself after each finished change** — a descriptive `git add <files> && git commit` per logical change. Do **not** leave changes for the sync service: it produces meaningless "sync …" messages and squashes unrelated edits together
- **Always include the current host in commit messages**. Prefix the subject with `[nixos-pc]` or `[nixos-laptop]` (for example: `[nixos-pc] enable CUDA cache` or `[nixos-laptop] add lid mode toggle`)
- **The sync service pushes tracked changes after every `nixos-rebuild`.** `home-manager/desktop/sync.nix` runs `scripts/sync.sh` after a rebuild (an HM `home.activation.syncAfterRebuild` hook restarts the oneshot). It does `git pull --rebase --autostash` → `git add -u` → `git commit` → `git push`. Note `add -u` (tracked-only) — new untracked files are _not_ picked up, so creating a new module and forgetting to `git add` it once will silently leave it out of upstream history. Pull before editing on the other host
- **`HUIX` env var / `huixDir` are runtime references to the live checkout** — consumed by scripts, aliases, and `source` includes on the running machine. Don't hardcode `/home/rokokol/huix` — use `$HUIX` in scripts and `huixDir` in Nix. But as a string, `"${huixDir}/…"` is **not copied into the store**, so it is useless for anything a build reads
- **Repo assets that a derivation consumes go through `inputs.self`, but BE VERY CAREFUL.** The string `"${inputs.self}/assets/..."` ties the derivation hash to the whole repository (any commit or file change triggers a rebuild). To avoid constant rebuilds and re-downloads on every config edit, **ALWAYS isolate paths via `builtins.path`**: `src = builtins.path { name = "my-assets"; path = "${inputs.self}/assets/..."; };`. This guarantees the derivation rebuilds only when the assets themselves change. Using `$HUIX` or `huixDir` inside derivations is not allowed (they don't land in the store). The rule is about **derivation inputs only** — `imports = [ "${inputs.self}/scripts/scripts.nix" ]` needs no `builtins.path`, because a module is read at eval time and only the values it produces reach any derivation (verified: an unrelated edit leaves `system.build.toplevel.drvPath` byte-identical). `huixDir` cannot be used there either way — it is a string, and importing an absolute path is forbidden under pure evaluation
- **Third-party flakes must reuse the system `nixpkgs` and `home-manager` via `follows`.** When adding new programs to `flake.nix` (e.g. `zen-browser`), always set `inputs.nixpkgs.follows = "nixpkgs";`, otherwise the third-party flake pulls its own copy of nixpkgs. That leads to duplicated packages, slow evaluation, and double downloads from the internet
- **PC user dirs depend on the `govno` NTFS mount** at `/home/rokokol/govno`. `xdg.userDirs` (Documents/Pictures/Videos) point there — it holds only files that must also be reachable from Windows. The mount has `nofail`, so boot survives without it but user paths break
- **The myWiki vault is `myWikiDir` = `$HOME/myWiki` on both hosts**, never derived from `rokokol.home.dataDir`. It sits on btrfs (Music lives inside it), and the path must stay host-invariant: Syncthing carries symlinks verbatim, so anything pointing into the vault — Claude memory buckets in `claude-shared/projects/*` above all — would dangle on the other host if the hosts disagreed
- **`users.users.${rokokolName}.extraGroups` is set in multiple modules** (`system.nix`, `nvidia.nix`, `docker.nix`, `virtualization.nix`). Nix module merge handles it, but when debugging permissions, grep all of `nixos/` rather than trusting one file
- **All service ports bind to `127.0.0.1`** (Ollama 11434, Open WebUI 8088, ComfyUI 8188, SearxNG 9000, Jupyter 8888, Syncthing GUI 8384, LibreTranslate 5000) and the firewall opens nothing for them. Don't change a bind address without a deliberate reason; if you must expose something, open the firewall explicitly in the same module
- **Cachix substituters are declared per-module** (`nixos/pc/nvidia.nix` → cuda-maintainers; `nixos/services/ai/comfyui.nix` → comfyui). When adding a heavy build, prefer adding a substituter over rebuilding
- **Light/dark theme is owned at runtime, NOT declaratively.** `scripts/toggle-theme.sh` (bind `SUPER+A`) flips `org/gnome/desktop/interface` `color-scheme`+`gtk-theme` in dconf and persists the choice to `~/.local/state/huix/theme`. Do **not** put `color-scheme`/`gtk-theme` in `home-manager/desktop/theme/theme.nix` `dconf.settings`, and do **not** set `gtk.theme` — the HM `gtk` module injects `gtk-theme` into dconf, so `dconf load` on every `nixos-rebuild` would clobber the runtime choice back to light (theme "slips"). The gruvbox theme is installed via `home.packages`. A _static baseline_ `gtk-theme-name` is declared via `gtk.gtk3/gtk4.extraConfig` (writes `settings.ini` only, never dconf) so apps that don't use the GtkSettings↔dconf bridge — `swayosd` (systemd-user service), `pavucontrol`, GTK file dialogs — don't fall back to Adwaita; this baseline does _not_ follow the runtime toggle. `icon-theme` (non-toggled) is declared in `dconf.settings`. `exec = toggle-theme.sh --sync` in `hyprland.conf` re-applies the saved choice on each reload. **libadwaita apps (gnome-text-editor, baobab…) ignore `gtk-theme-name` entirely** — they only pick up gruvbox from `~/.config/gtk-4.0/gtk.css`, so `toggle-theme.sh` symlinks the active variant there. It links **only the colour definitions** (`gtk-colors.css`, split out by the theme package's `postInstall`), never the full sheet: every GTK4 app parses this file on startup and on each toggle, and the full 232K sheet costs ~15ms a parse plus hundreds of icon lookups versus 0.12ms for the 7K colours — which is all libadwaita honours anyway (non-libadwaita GTK4 apps get their styling from `gtk-theme-name`). No `assets` symlink is needed since the colour lines carry no `url()`. Paths come from `GTK4_LIGHT_CSS`/`GTK4_DARK_CSS`, exported by `theme.nix` as `home.sessionVariables` — so **a fresh login is required** after adding/changing them before the toggle sees them; already-running libadwaita apps don't restyle live, reopen them
- **Screen zoom differs by input device.** `scripts/zoom.sh` (live magnifier around the cursor via `cursor:zoom_factor`) is bound to `ALT+WIN+wheel` in `hyprland.conf` — but Hyprland `mouse_up`/`mouse_down` binds fire **only for a physical mouse wheel, never a touchpad** (no input option changes this; `emulate_discrete_scroll` does not help). So on the laptop, touchpad zoom is a separate `gesture = 2, pinch, cursorZoom, 1, live` (Hyprland's built-in continuous pinch-zoom — the gesture engine has no generic `exec`, so it can't call `zoom.sh`). Two mechanisms, same feel; keep both
- **Power button shows a menu, not instant poweroff.** `services.logind.settings.Login.HandlePowerKey = "ignore"` (`nixos/desktop/logind.nix`) hands the power key to Hyprland, which binds `XF86PowerOff` → `scripts/rofi-power.sh` (a rofi script-modi named `power`; its ⚡ prompt emoji comes from `display-power` in `home-manager/programs/rofi.nix`, the single source of mode emojis). Without the logind override the system would poweroff immediately, bypassing the menu
- **Lid mode (laptop only) is an inhibitor lock, not a logind override.** `SUPER+SHIFT+A` → `scripts/lid-mode.sh toggle` starts the transient user unit `huix-lid-inhibit` holding `systemd-inhibit --what=handle-lid-switch --mode=block`; while it lives, closing the lid doesn't suspend and Hyprland's `bindl = , switch:on:Lid Switch` (emitted from `home-manager/desktop/hyprland/services/lid-mode.nix`, gated by `rokokol.hyprland.lidNoSleep`) only does `dpms off`. The lock is effective **only** because `nixos/laptop/logind.nix` sets `LidSwitchIgnoreInhibited = "no"` — logind ignores lid inhibitors by default. `HandleLidSwitch` is deliberately left at `suspend` (unlike the power key), so outside the Hyprland session — greeter, tty, crashed compositor — the lid still suspends. State is _only_ the unit's active-ness (no state file, nothing to restore on reload): the mode is intentionally session-scoped so a reboot can't leave the laptop awake in a bag. Binds live in HM `settings`, not in the shared `hyprland.conf`, and are emitted before it is sourced — `$mainMod` isn't defined yet there, hence the literal `SUPER SHIFT`. There is deliberately **no waybar indicator** — the only feedback is the `notify-send` on toggle. `close`/`open` blank just the internal panel (`eDP*`/`LVDS*`/`DSI*` from `hyprctl monitors`), so an attached external monitor stays on
- **Full-screen shaders / software brightness now live in [rokokol/hyprland-screen-shader](https://github.com/rokokol/hyprland-screen-shader)**, a flake input. huix keeps two seams plus the keys: `home-manager/desktop/hyprland/services/screen-shader.nix` turns it on, `waybar/shader.nix` hands it `enable`, the RT-signal number (8 — notifications own 9) and the bar name, and the binds (`SUPER+SHIFT+G` picker, `SUPER+G` clear, `SUPER+CTRL+[`/`]`/`BackSpace` brightness) sit in `hyprland.conf` with every other bind. The module writes exactly one line of its own — `exec = screen-shader restore`, needed because the shader slot is lost on every reload — so do **not** add that one to `hyprland.conf`. Two commands: `screen-shader` is silent (messages to stderr) and `rofi-shader` is the UI layer that opens the picker or runs the manager and shows a popup, which is why the keys call `rofi-shader` while the waybar scroll calls `screen-shader`. `bar.nix` still decides where the indicator sits. State lives in `~/.local/state/screen-shader/state`; adding an effect is `programs.screen-shader.extraShaders`, not a file in this repo
- **The wooordhunt dictionary lives in [rokokol/rofi-wooordhunt](https://github.com/rokokol/rofi-wooordhunt)**, a flake input. huix keeps one seam: `home-manager/desktop/hyprland/services/rofi-wooordhunt.nix` turns it on and picks the 🤓 prompt; the `SUPER+Y` bind is in `hyprland.conf` like every other bind, and it is just `rofi-wooordhunt` — that binary is a launcher, and the parser it hands rofi lives off PATH in the package's `libexec`. The mode names itself over the script protocol (`\0prompt`), so the mode emoji is `programs.rofi-wooordhunt.prompt`, **not** a `display-dictionary` line in `programs/rofi.nix`, and there is no script under `scripts/` to edit. The parser's wrap widths default to a 720px window, which is `ddlc.rofi.width`'s default; a wider window means setting `wrapWidth`/`headWidth` in the seam
- **The rofi theme lives in [rokokol/ddlc-rofi-theme](https://github.com/rokokol/ddlc-rofi-theme)**, a flake input. huix keeps one seam: `home-manager/programs/rofi.nix` sets `ddlc.rofi.enable` plus the three fonts the theme ships none of (`Doki 12`/`13`, DepartureMono) — everything else there is rofi's own config (modi, `display-*`, plugins). The module deploys both variants into `~/.config/rofi/themes` and sets `programs.rofi.theme = "ddlc"`, so **do not** write a `config.rasi` or override `configPath` again: `~/.config/rofi/themes` is a directory rofi resolves theme names in by itself. Light/dark is a symlink there (`ddlc.rasi`), moved by the `ddlc-rofi-theme` command — `toggle-theme.sh` calls it and owns nothing else about rofi, and the module only picks a variant on the first activation, so a rebuild never resets the runtime choice. The background SVGs are named, not pathed, because rofi looks a bare image name up in that same flat directory rather than next to the theme that named it
- **Claude Code profile switching lives in [rokokol/claude-account](https://github.com/rokokol/claude-account)**, a flake input. huix keeps one seam: `home-manager/programs/cli/claude.nix` enables it and installs `pkgs.claude-code`. The module pins `CLAUDE_CONFIG_DIR` and runs `claude-account ensure` after `linkGeneration` on every activation — do **not** add either back here, and there is no script under `scripts/` to edit. The dirs it uses (`~/.local/share/claude-profiles`, `~/.local/share/claude-shared`) are the module's defaults, so huix names none of them; changing what the profiles share is `programs.claude-account.sharedEntries`
- **The virtual camera and microphone live in [rokokol/virtual-media-devices](https://github.com/rokokol/virtual-media-devices)**, a flake input, and the two seams sit in different layers on purpose. The camera needs a kernel module, so it is NixOS: `services.virtual-media-devices.camera` is set directly in `nixos/configuration-pc.nix` (PC only — the laptop must not load `v4l2loopback`), with no `rokokol.*` alias in front of it. The microphone needs nothing system-level, so it is HM: `home-manager/programs/virtual-mic.nix`, one line, both hosts. There are no `scripts/virtual-*.sh` to edit any more. The card label and the `/dev/videoN` are declared once as `camera.{label,videoNr}` and the module hands them to the command as `VIRTUAL_CAM_LABEL`/`VIRTUAL_CAM_DEVICE` — before the split they were written into the modprobe line _and_ hardcoded in the script, free to drift apart. `camera.users = [ rokokolName ]` is what puts the user in `video`; it duplicates `nixos/system.nix` deliberately, because a module has to declare what it depends on rather than lean on a line in someone else's config. On this desktop the group is not what actually grants access — systemd's `70-uaccess.rules` hands `/dev/video*` to the active local session — but it is what covers a session `uaccess` never reaches
- **The lock screen lives in [rokokol/ddlc-hyprlock](https://github.com/rokokol/ddlc-hyprlock)**, a flake input — the hyprlock config, Monika's dialog engine and the assets it speaks from all left together, so there is no `scripts/hyprlock-quote.sh` and no `assets/just-monika.png` here any more. huix keeps one seam: `home-manager/desktop/hyprland/services/hyprlock.nix` sets `ddlc.hyprlock.enable`, the `Doki` font the theme ships none of, and `screenShader` — which is also what picks `flash = "screen-shader"`, so **do not** set `flash` here as well. That choice matters on this desktop: the module's dependency-free `hyprctl` mode ends a flash by emptying `decoration:screen_shader`, which would wipe whatever `screen-shader` had on screen, while handing the flash to `screen-shader` composites it over the active effect and puts that back. What runs a lock is the module's read-only `ddlc.hyprlock.lockCommand`, which `services/hypridle.nix` puts in `lock_cmd`: the engine has to be hyprlock's **parent** (it blocks for the whole lock and never kills the locker), so nothing may call `hyprlock` directly and no bind may call the engine either — `SUPER+F12` goes through `loginctl lock-session` like every other lock path. `dialog` is on by default and `home-laptop.nix` turns it off — two shell-spawning labels at 10 Hz plus a render loop is not a battery feature — and with it off `lockCommand` is plain hyprlock. The geometry, the colours and the labels are one attrset in the module's `nix/config.nix`; the text-area width it computes is handed to the engine, so **do not** set `programs.hyprlock.settings` here to nudge the layout: a label moved without the engine's wrap width moving with it is exactly what that single source of truth prevents
- **Workarounds that exist only because of an upstream bug live in `workarounds.md`**, one entry each with a mechanical removal check. Add new ones there rather than here, and check it before "cleaning up" a line that looks pointless
- **Notification center** lives in `scripts/notify-center.sh` (+ `scripts/rofi-notify.sh`, waybar module in `waybar/notifications.nix`, both hosts). DND is a mako mode (`[mode=do-not-disturb] invisible=1`) — runtime-only, resets with the mako process, no restore-on-reload needed. The rofi list shows the whole feed as-is; the only per-entry op is copying the text — notification _actions_ are deliberately not exposed there (they only work natively on displayed popups: left-click = default action, right-click = `makoctl menu`; `makoctl invoke` on history entries silently no-ops). History is cleared only as a whole (`clear`), and since makoctl has no history-clear command, `clear` restores+dismisses every entry under a second invisible mode (`silent`) so popups don't flash — that's the only use of `silent`. Waybar indicator uses `SIGRTMIN+9` (`WAYBAR_NOTIF_SIGNAL`, declared in `waybar/notifications.nix`; shader owns 8) — same RT-signal rules as above, but here signals only fire on user actions, so no startup suppression is needed. The indicator counts the _feed_ = currently displayed popups + history (counting history alone makes on-screen notifications invisible to the counter). Manual close bypasses history (history holds only notifications that expired unseen): popup middle-click via the native `dismiss --no-history` binding action, waybar-module middle-click via `makoctl dismiss -a -h`. **mako never re-reads its config by itself**, and nothing restarts it on a rebuild: HM's `services.mako` creates no unit at all — it installs the package, registers `dbus.packages` and writes `~/.config/mako/config`, nothing more. The daemon is the package's own `mako.service` (`Type=dbus`, `BusName=org.freedesktop.Notifications`, plus a D-Bus activation file), started by `exec-once = systemctl --user start mako.service` in `hyprland.conf`; don't put a bare `exec-once = mako` back, it would grab the bus name outside systemd and leave the `Type=dbus` unit fighting an owner it doesn't manage. Reloading it is HM's job and already handled: the module puts `onChange = "makoctl reload"` on `~/.config/mako/config`, which runs inside `onFilesChange` (ordered `entryAfter [ "linkGeneration" ]`) and only when the config actually changed. Do **not** add a `home.activation.*` reload of your own next to it — one lived here on `entryAfter [ "writeBoundary" ]`, the same anchor `linkGeneration` uses, so nothing ordered the two and it could run before the config link was in place — and **`makoctl reload` against a missing config resets the daemon to its stock defaults and still exits 0**, silently. **Every colour must be set in the global block, never only inside an `[urgency=…]` section.** mako's criteria are `low`/`normal`/`critical` and there is no criterion for "sender omitted the urgency hint" — such notifications match no section at all and keep whatever the global block left unset, which is mako's stock blue (`#285577`). Telegram and Firefox both omit the hint, so for a long time every chat and web notification came out blue while `notify-send` (which always sends one) looked right. The global block therefore doubles as the style for that category — its own ground, since "no hint" is orthogonal to loudness — and `[urgency=normal]` styles only senders that genuinely say normal
